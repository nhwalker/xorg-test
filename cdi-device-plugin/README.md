# cdi-device-plugin

A small, generic kubelet device plugin that makes **one CDI device
requestable as one extended resource**.

It carries no knowledge of any particular device. It never constructs
mounts, environment variables, or device nodes — the CDI spec on the node
is the single source of truth for what injection means, and this process
only routes a resource request to a CDI device name:

```
CDI_DEVICE=desktop.local/display=all
RESOURCE_NAME=desktop.local/display
```

A pod requesting `desktop.local/display` then receives whatever
`/etc/cdi/desktop-display.yaml` says that device injects. Point it at any
CDI device on the node; install one release per device.

## Why this exists

CDI injection is the container runtime's job, and a container asks for a
CDI device by naming it. Under podman that is a flag:

```sh
podman run --device desktop.local/display=all <image>
```

Kubernetes has no equivalent pod field, and — this is the part that
surprises people — **a `cdi.k8s.io/...` pod annotation does not work.**
It fails silently: the pod is created, nothing is injected, and no error
is reported anywhere.

The reason is in kubelet. A container's CRI annotations are built by
`newContainerAnnotations` from `opts.Annotations` plus kubelet's own
bookkeeping labels; pod annotations are never copied in. Upstream is
explicit about what that field is for:

```go
// The annotations for the container
// These annotations are generated by other components (i.e.,
// not users). Currently, only device plugins populate the annotations.
Annotations []Annotation
```
<sub>`pkg/kubelet/container/runtime.go`, `RunContainerOptions`</sub>

There is no container-level annotation either — `v1.Container` has no
metadata field at all. And both runtimes read the *container* config, not
the sandbox: CRI-O's `SpecInjectCDIDevices` parses
`c.Config().GetAnnotations()` (unchanged 1.29 → main), and containerd
calls `customopts.WithCDI(config.Annotations, config.CDIDevices)`.

So both doors into the runtime's CDI injection are device-plugin doors.
This plugin is the smaller one: `Allocate()` returns `CDIDevices` naming
the configured device, kubelet passes it through the CRI `CDIDevices`
field, and the runtime applies the spec.

(The other door is DRA, which is the better long-term answer once a
cluster is on a version where it is GA.)

## Quick start

```sh
helm install display charts/cdi-device-plugin \
    --set image.repository=<registry>/cdi-device-plugin \
    --set cdiDevice=desktop.local/display=all \
    --set count=10
```

```sh
kubectl describe node | grep -A1 desktop.local/display   # 10 allocatable
```

A client then declares only the request — no volumes, no env:

```yaml
resources:
  limits:
    desktop.local/display: 1
```

## Configuration

Chart values map one-to-one onto the binary's environment.

| Value | Env | Default | Meaning |
|---|---|---|---|
| `cdiDevice` | `CDI_DEVICE` | *(required)* | Fully qualified CDI device, `vendor/class=device`. Rejected at startup if malformed. |
| `resourceName` | `RESOURCE_NAME` | the device's CDI kind | Extended resource pods request. |
| `count` | `COUNT` | `1` | Interchangeable copies to advertise. |
| `cdiSpecDirs` | `CDI_SPEC_DIRS` | `/etc/cdi,/var/run/cdi` | Where to look for specs. Must match the runtime's own spec dirs. |
| `healthInterval` | `HEALTH_INTERVAL` | `5s` | How often the spec dirs are rescanned. |
| `kubeletPluginDir` | `PLUGIN_DIR` | `/var/lib/kubelet/device-plugins` | Kubelet's registration directory. |

### `resourceName`

Defaults to the device's kind (`desktop.local/display=all` →
`desktop.local/display`), which is already vendor-qualified and therefore
a legal extended resource name. Override it when that would collide with
another plugin on the node — e.g. advertise `nvidia.com/gpu=all` as
`desktop.local/gpu` on a node where NVIDIA's own plugin already owns
`nvidia.com/gpu`.

### `count` and sharing

The device plugin API allocates **exclusively**. For a genuinely
exclusive device leave `count` at 1. For a *shareable* device — a display,
say — `count` is simply the maximum number of concurrent claimants; the
copies are interchangeable and all resolve to the same CDI device.

### Health

A device is Healthy while it resolves in the configured spec dirs, and
Unhealthy once it stops resolving (spec deleted, or rewritten without it).
That is the same lookup the runtime performs at container creation, so a
Healthy resource is one the runtime can actually inject — pods stay
Pending on a node whose spec is missing, instead of failing at container
creation with an unresolvable-device error.

Health is deliberately *not* a probe of whether the underlying thing
works. Whether an X server is actually listening behind an injected socket
is the client's problem, not this plugin's.

## One resource per deployment

Kubelet's `Register` call takes a single resource name, so serving N
devices means running N releases. That is the intended shape: each
deployment is independently debuggable, and the binary stays small.

```sh
helm install display charts/cdi-device-plugin --set cdiDevice=desktop.local/display=all --set count=10
helm install audio   charts/cdi-device-plugin --set cdiDevice=desktop.local/audio=all   --set count=10
helm install gpu     charts/cdi-device-plugin --set cdiDevice=nvidia.com/gpu=all --set resourceName=desktop.local/gpu
```

Separate releases also mean separate counts and independent health, so a
client can be granted one capability without the other — which is the
point of splitting the desktop into `display` and `audio` devices rather
than one combined device.

## What it deliberately does not do

- **Build injections.** No mounts, no env, no device nodes. If a client
  needs something, it belongs in the CDI spec, where podman clients get
  it too.
- **Relabel for SELinux.** CDI `containerEdits` has no equivalent of
  `-v src:dst:z`, so on an enforcing host a *confined* container may
  receive its mounts and still be denied on use. Labeling the underlying
  paths is host-side work.
- **Scheduling policy.** Beyond `count` and health, allocation is
  kubelet's business.

## Testing

`go test ./...` runs the plugin against a fake kubelet over real gRPC
sockets, driving health transitions by **writing and removing actual CDI
spec files** — so what is under test is the same resolution the runtime
does, not a stub of it. `Allocate` is asserted to return `CDIDevices` and
*no* mounts or envs, since duplicating the spec is the bug this design
exists to avoid.

The repo's VM e2e exercises the whole path on a live k3s + CRI-O node: the
resources becoming allocatable, a pod that declares nothing but its
requests reaching an X display and playing audio, a control pod that
requests nothing and must receive nothing, and narrow pods proving each
device grants its own capability and *not* the other's.

## A note on upstream

`container-device-interface` v1.1.0 panics on a single-character vendor or
class name (`validateVendorOrClassName` slices `name[1:len(name)-1]`
without a length guard, so `a/b=c` panics rather than erroring).
`parseQualifiedName` contains that, so a typo in `CDI_DEVICE` produces a
readable startup error instead of a stack trace.
